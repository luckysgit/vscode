## 1. Project Overview

**CodeBattle** is a real-time competitive coding platform where users can:
- Create private or public coding rooms with unique codes or QR codes
- Compete with friends, strangers, or AI in real-time
- Solve problems in 10+ programming languages (Python, JavaScript, TypeScript, Java, C++, C#, Go, Rust, PHP, Swift)
- Earn XP, unlock badges, and climb the global leaderboard
- Conduct live coding interviews
- Play daily challenges with streaks
- Publish custom problems for others to solve
- Connect with other coders (mutual connections only)
- Subscribe to Pro tier for advanced features

Key differentiators:
- No followers/following system — only mutual connections
- Real-time leaderboard as players code
- Code is never visible to other players (only results)
- Anonymous participation supported
- Fully functional offline with local fallbacks

## 5. Environment Variables Guide

Create a `.env.local` file in the root directory. All variables are optional — the app falls back to local/demo mode if missing.

### Supabase (Database & Auth Metadata)
```env
# Get from https://supabase.com → New Project → Settings → API
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...your-anon-key
SUPABASE_SERVICE_ROLE_KEY=eyJ...your-service-role-key
```
- Service role key is for server-side operations only
- Anon key is for client-side queries (restricted by Row Level Security)

### Clerk (Authentication)
```env
# https://dashboard.clerk.com → Hamburger menu → API Keys
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...or pk_live_
CLERK_SECRET_KEY=sk_test_...or sk_live_
CLERK_WEBHOOK_SECRET=whsec_...

# After setting up Clerk app
NEXT_PUBLIC_CLERK_SIGN_IN_URL=/sign-in
NEXT_PUBLIC_CLERK_SIGN_UP_URL=/sign-up
NEXT_PUBLIC_CLERK_AFTER_SIGN_IN_URL=/dashboard
NEXT_PUBLIC_CLERK_AFTER_SIGN_UP_URL=/onboarding
```
- Set up webhook at `https://yourdomain.com/api/webhooks/clerk`
- Enable events: `user.created`, `user.updated`, `user.deleted`

```env
# https://console.upstash.com → Create Database
```

## 6. Complete Setup Instructions (From Scratch)

### Prerequisites
- Node.js 18+ (preferably 20)
- npm or yarn
- Git
- PostgreSQL client tool (for Supabase SQL editor)

### Step 1: Clone & Install
```bash
git clone <repo-url>
cd codebattle
npm install
```

### Step 2: Create .env.local
```bash
cp .env.local .env.local  # Copy template
# Edit .env.local and fill in keys
```

### Step 3: Local Development (No External Services)
Start with everything disabled to test locally:
```env
NODE_ENV=development
NEXT_PUBLIC_APP_URL=http://localhost:3000
NEXT_PUBLIC_WS_URL=http://localhost:3001
WS_PORT=3001
```

This gives you:
- User registration with local file-based storage (`.data/users.json`)
- Problems and problists from seed data
- Socket.io room support (in-memory, no persistence)
- Code execution via free Piston API

### Step 4 (Optional): Set Up Supabase
1. Go to https://supabase.com and create a new project
2. In SQL Editor, run `supabase/schema.sql` (creates all tables + RLS)
3. Then run `supabase/seed.sql` (adds 10 starter problems)
4. Go to Settings → API and copy keys into `.env.local`

### Step 5 (Optional): Set Up Clerk
1. Go to https://clerk.com and create an app
2. Enable OAuth providers: Google, GitHub, Email
3. Go to API Keys and copy keys
4. Set up webhook at: Settings → Webhooks → Add Endpoint
   - URL: `https://yourdomain.com/api/webhooks/clerk`
   - Events: `user.created`, `user.updated`, `user.deleted`
5. Copy keys to `.env.local`

### Step 6 (Optional): Set Up Stripe
1. Go to https://dashboard.stripe.com
2. Create a product "Pro Plan" — $9/month recurring
3. Go to Developers → API Keys
4. Copy Secret Key to `.env.local`
5. Create a webhook endpoint:
   - URL: `https://yourdomain.com/api/payments/webhook`
   - Events: `checkout.session.completed`

### Step 7 (Optional): Set Up Resend
1. Go to https://resend.com and sign up
2. Create API key
3. Verify your domain (or use demo email)
4. Copy key to `.env.local`

### Step 8 (Optional): Set Up Judge0
For production code execution, deploy Judge0 or use RapidAPI hosted version.

## 9. Supabase Database Setup

### Running schema.sql
```sql
-- Copy entire supabase/schema.sql
-- Go to Supabase → SQL Editor → New Query → Paste → Run
```

Creates these tables:
- `users` — User profiles + XP
- `connections` — Mutual friend graph
- `problems` — Coding problems
- `test_cases` — Test cases per problem
- `rooms` — Multiplayer game rooms
- `submissions` — Code submissions + results
- `problists` — Custom problem collections
- `badges` — User achievements
- `problem_flags` — Content reports

### Running seed.sql
Adds 10 starter problems with test cases:
1. Two Sum (easy)
2. Reverse String (easy)
3. FizzBuzz (easy)
4. Palindrome Check (easy)
5. Maximum Subarray (medium)
6. Valid Parentheses (medium)
7. Binary Search (medium)
8. Merge Two Sorted Arrays (medium)
9. Climbing Stairs (hard)
10. LRU Cache (hard)

Plus 4 problem collections (Beginner, Interview, Data Structures, DP)

### Row Level Security (RLS)
All tables have RLS enabled:
- Users can only read/modify their own data
- Problems marked "public" are visible to all
- Submissions visible only to submitter

   - `http://localhost:3000/sign-in` (dev)
   - `https://yourdomain.com/sign-in` (production)

### Webhook Configuration
Clerk sends events to `/api/webhooks/clerk` when:
- User created → Create entry in `users` table
- User updated → Update avatar/email
- User deleted → Soft delete or cascade

### Flow: Signup → Webhook → Supabase
```
Clerk Signup Form
      ↓
Clerk creates user_id
      ↓
Webhook POST to /api/webhooks/clerk
      ↓
Create entry in supabase.users
      ↓
Send welcome email via Resend
```

## 14. API Route Documentation

### Authentication Routes

#### `POST /api/auth/register`
**Requires**: No auth
**Rate limit**: 3/60s
**Body**:
```json
{
  "username": "newuser",
  "email": "user@example.com",
  "password": "securepass123",
  "language": "Python"
}
```
**Response** (201):
```json
{
  "user": { "id": "...", "username": "newuser", "email": "...", "xp": 0, "rank": "Bronze", ... },
  "success": true
}
```
**Sets Cookie**: `cb_session` (base64 encoded session token for local auth)
**Path**: Local dev only (when Supabase not configured) or falls through to Clerk

#### `POST /api/auth/login`
**Requires**: No auth
**Rate limit**: 5/60s
**Body**:
```json
{
  "email": "user@example.com",
  "password": "securepass123"
}
```
**Response** (200): Same as register

#### `POST /api/auth/logout`
**Requires**: Auth
**Response** (200): `{ "success": true }`
**Clears**: `cb_session` cookie

#### `GET /api/auth/me`
**Requires**: Auth
**Response** (200):
```json
{
  "user": { "id": "...", "username": "...", "email": "...", "tier": "free", ... }
}
```

#### `POST /api/auth/forgot-password`
**Body**: `{ "email": "user@example.com" }`
**Sends**: Reset link via Resend
**Response** (200): `{ "message": "Reset email sent" }`

#### `POST /api/auth/reset-password`
**Body**: `{ "token": "...", "password": "newpass123" }`
**Response** (200): `{ "success": true }`

### Submission Routes

#### `POST /api/submissions`
**Requires**: Auth
**Rate limit**: 10/10s
**Body**:
```json
{
  "code": "print('hello')",
  "language": "Python",
  "problemId": "1",
  "roomId": "optional-room-id",
  "stdin": "optional-single-test-input"
}
```
**Behavior**:
- If `stdin` provided: Run against single test case (development mode)
- Otherwise: Run against all test cases (submit mode)

**Response** (200):
```json
{
  "results": [
    { "passed": true, "actual": "output", "expected": "output", "hidden": false },
    { "passed": false, "actual": "wrong", "expected": "correct", "hidden": false }
  ],
  "testsPassed": 1,
  "testsTotal": 2,
  "allPassed": false,
  "score": 50,
  "xpEarned": 0,
  "status": "wrong_answer"
}
```
**Side effects**:
- Saves submission to DB
- If all passed: Award XP + update streak
- If first try all passed: Award "clean_code" badge
- Broadcasts result to room via Socket.io

## 16. Socket.io Event Map

All events are JSON (no binary). Server is at `/server/index.ts`.

### Client → Server

#### `room:join`
**Sent when**: User clicks "Join Room"
**Data**:
```typescript
{
  roomCode: string;      // "ABC123"
  userId: string;        // From auth
  username: string;      // Display name
}
```
**Server does**: Adds player to room, broadcasts `room:player_joined`

#### `room:leave`
**Sent when**: User closes room tab or clicks "Leave"
**Data**: `{ roomCode, userId }`
**Server does**: Removes player, broadcasts `room:player_left`

#### `room:start`
**Sent when**: Host clicks "Start Countdown"
**Data**: `{ roomCode, userId }`
**Validation**: Only host can start
**Server does**: Broadcasts `room:countdown { seconds: 5 }`

#### `submission:result`
**Sent when**: Client receives results from POST `/api/submissions`
**Data**:
```typescript
{
  roomCode: string;
  userId: string;
  testsPassed: number;   // e.g., 3
  testsTotal: number;    // e.g., 5
  score: number;         // 0-100
  allPassed: boolean;
}
```
**Server does**: Updates player score, broadcasts `room:progress_update` to all players

#### `room:activity`
**Sent when**: User types code / interacts
**Data**: `{ roomCode, userId }`
**Server does**: Broadcasts `room:activity_pulse { userId }` to show "User is typing..."

#### `room:reaction`
**Sent when**: User clicks emoji reaction
**Data**: `{ roomCode, userId, emoji: "��" }`
**Server does**: Broadcasts `room:reaction` to all players (emoji animation over their name)

#### `interview:join`
**Sent when**: Candidate or interviewer joins interview
**Data**: `{ sessionCode, role: "candidate" | "interviewer", userId }`
**Server does**: Broadcasts `interview:user_joined`

#### `interview:code_update`
**Sent when**: Candidate types code
**Data**: `{ sessionCode, code: string, language: string }`
**Server does**: Broadcasts to interviewer only (real-time code view)

#### `interview:leave`
**Sent when**: Interview ends
**Data**: `{ sessionCode }`

---

### Server → Client

#### `room:player_joined`
**Broadcasted to**: All players in room
**Data**: `{ userId, username, playerCount }`
**Effect on client**: Add player to leaderboard, update player count

#### `room:state`
**Sent to**: Player who just joined
**Data**:
```typescript
{
  code: string;
  status: "lobby" | "countdown" | "active" | "ended";
  players: { userId, username, score, testsPassed, finished }[];
  language: string;
  difficulty: string;
  timerType: string;
  timeLimitSec: number;
}
```

#### `room:countdown { seconds: 5 }`
**Broadcasted to**: All players in room
**Effect on client**: Show big countdown timer

#### `room:tick { seconds: 4 }`
**Broadcasted**: Every 1 second during countdown

#### `room:started`
**Broadcasted**: When countdown reaches 0
**Data**: `{ startedAt: timestamp, timeLimitSec: 1800 }`
**Effect on client**: 
- Hide countdown
- Enable code editor
- Start timer countdown

#### `room:progress_update`
**Broadcasted to**: All players in room
**Data**:
```typescript
{
  userId: string;
  testsPassed: number;
  testsTotal: number;
  score: number;
  allPassed: boolean;
  leaderboard: { rank, userId, username, score, testsPassed, finished }[];
}
```
**Effect on client**: Update leaderboard, show score changes

#### `room:player_finished`
**Broadcasted**: When a player passes all tests first
**Data**: `{ userId, rank: 1, score: 100, timeTakenMs: 234000 }`
**Effect on client**: Show "alice finished in 3:54! ��"

#### `room:player_left`
**Broadcasted**: When player leaves
**Data**: `{ userId, playerCount: 3 }`
**Effect on client**: Remove from leaderboard

#### `room:ended`
**Broadcasted**: When all players finish or timer expires
**Data**: `{ leaderboard: [...], endedAt: timestamp }`
**Effect on client**: Show results screen, disable editor

#### `room:activity_pulse { userId }`
**Broadcasted**: When user types
**Effect on client**: Show "typing..." indicator next to player name

#### `room:reaction { userId, emoji }`
**Broadcasted**: When user reacts
**Effect on client**: Float emoji animation over player's name

#### `interview:user_joined`
**Sent to**: Other participant
**Data**: `{ role: "candidate" | "interviewer", userId }`

#### `interview:code_update`
**Sent to**: Interviewer
**Data**: `{ code: string, language: string }`
**Effect**: Update code view in real-time

#### `error`
**Sent**: On validation/auth failure

## 17. Database Schema with Relationships

### users
```sql
CREATE TABLE users (
  id UUID PRIMARY KEY,
  clerk_id TEXT UNIQUE NOT NULL,        -- Clerk user ID (production)
  username TEXT UNIQUE NOT NULL,
  email TEXT UNIQUE NOT NULL,
  avatar_url TEXT,
  tier TEXT ('free', 'paid') DEFAULT 'free',
  xp INTEGER DEFAULT 0,                 -- Experience points
  rank TEXT ('Bronze', 'Silver', ...) DEFAULT 'Bronze',
  streak INTEGER DEFAULT 0,             -- Days solved consecutively
  last_solve_at TIMESTAMP,              -- Last problem solved date
  stripe_customer_id TEXT,              -- For Stripe subscriptions
  created_at TIMESTAMP DEFAULT NOW()
);

-- Indexes
CREATE INDEX idx_users_clerk_id ON users(clerk_id);
CREATE INDEX idx_users_username ON users(username);
CREATE INDEX idx_users_xp ON users(xp DESC);  -- For leaderboard query
```

**Relationships**:
- 1 user → many problems (author_id)
- 1 user → many connections (user_a_id, user_b_id)
- 1 user → many submissions (user_id)
- 1 user → many badges (user_id)

---

### connections (Mutual Friends Graph)
```sql
CREATE TABLE connections (
  id UUID PRIMARY KEY,
  user_a_id UUID REFERENCES users(id) ON DELETE CASCADE,
  user_b_id UUID REFERENCES users(id) ON DELETE CASCADE,
  connected_at TIMESTAMP DEFAULT NOW(),
  UNIQUE(user_a_id, user_b_id),
  CHECK (user_a_id < user_b_id)  -- Ensures no duplicates (a->b = b->a)
);

CREATE INDEX idx_connections_a ON connections(user_a_id);
CREATE INDEX idx_connections_b ON connections(user_b_id);
```

**Purpose**: Mutual connection tracking (no followers/following)
**Invariant**: user_a_id < user_b_id ensures single row per pair

---

### problems
```sql
CREATE TABLE problems (
  id UUID PRIMARY KEY,
  author_id UUID REFERENCES users(id) ON DELETE SET NULL,
  forked_from UUID REFERENCES problems(id),  -- Problem versioning
  version INTEGER DEFAULT 1,
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  difficulty TEXT ('easy', 'medium', 'hard'),
  visibility TEXT ('public', 'private', 'connections') DEFAULT 'public',
  unique_code TEXT UNIQUE,                -- Short code like "TWOSUM"
  language_tags TEXT[] (e.g., ['array','hashmap']),
  input_format TEXT,                      -- How input is formatted
  output_format TEXT,                     -- How output is formatted
  solve_count INTEGER DEFAULT 0,          -- Auto-updated on submissions
  avg_solve_ms INTEGER,                   -- Average solve time
  is_flagged BOOLEAN DEFAULT false,       -- Reported as inappropriate
  is_approved BOOLEAN DEFAULT true,       -- Admin approved
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_problems_visibility ON problems(visibility) WHERE visibility = 'public';
CREATE INDEX idx_problems_difficulty ON problems(difficulty);
```

**Visibility levels**:
- `public` — anyone can see/solve
- `private` — only author
- `connections` — only connections of author

### test_cases

### submissions
```sql
CREATE TABLE submissions (
  id UUID PRIMARY KEY,
  room_id UUID REFERENCES rooms(id) ON DELETE SET NULL,
  user_id UUID REFERENCES users(id) ON DELETE SET NULL,
  problem_id UUID REFERENCES problems(id) ON DELETE SET NULL,
  language TEXT NOT NULL,
  code TEXT NOT NULL,
  status TEXT ('pending','accepted','wrong_answer','time_limit','runtime_error','compile_error'),
  tests_passed INTEGER DEFAULT 0,
  tests_total INTEGER DEFAULT 0,
  score INTEGER DEFAULT 0,               -- 0-100
  time_taken_ms INTEGER,                 -- Time to solve in ms
  submitted_at TIMESTAMP DEFAULT NOW()
) PARTITION BY RANGE (submitted_at);    -- Partition for old data archive

-- Auto-trigger: increment problems.solve_count on accepted
```

**Lifecycle**:
1. Created as "pending" when user submits
2. Worker (`workers.ts`) runs code against all test cases
3. Updated to "accepted" (all pass) or "wrong_answer" (some fail)
4. If accepted: XP awarded, streak updated, badges checked

## 18. Security Implementation

### Authentication
- **Production**: Clerk OAuth (industry-standard)
- **Development**: Local file-based auth (`lib/auth.ts`)
- **Session storage**:
  - Clerk: Session cookie (`__session`)
  - Local: Encrypted cookie (`cb_session` — base64 JSON)

### Authorization
- **Route protection**: `middleware` checks auth before protected routes
- **API auth**: `requireAuth()` in every protected API route
- **Admin check**: `ADMIN_EMAILS` environment variable

### Input Validation
- **Zod schemas** in API routes validate all inputs
- **Sanitization** of HTML content via `isomorphic-dompurify`
- **Code submissions**: Limited to 50KB max size

### Rate Limiting
- **Production**: Upstash Ratelimit (Redis-backed)
- **Development**: In-memory sliding window
- **Limits**:
  - Login: 5/60s per IP
  - Register: 3/60s per IP
  - Code submission: 10/10s per user
  - Room creation: 5/60s per user

### Database Security
- **Row Level Security (RLS)** enabled on all sensitive tables
- **Policy enforcement**:
  - Users see only own submissions
  - Public problems visible to all
  - Private problems visible only to author
- **Audit logging** of admin actions

### Code Execution Sandboxing
- **Judge0**: Isolated Docker containers, CPU/memory limits
- **Piston API**: Public sandbox (free tier, limited)
- **Timeouts**: 5-second execution limit
- **Network**: Disabled for all user code

### HTTPS & Headers
- **Content-Security-Policy**:
  - Blocks inline scripts except Monaco editor
  - Allows scripts from CDN only
  - Blocks camera/microphone unless explicitly requested
- **X-Frame-Options**: DENY (no clickjacking)
- **X-Content-Type-Options**: nosniff
- **Referrer-Policy**: strict-origin-when-cross-origin
- **HSTS**: (should add in production)

### Password Security (Local Auth)
- **bcryptjs**: 12 rounds (slowhash)
- **Never stored in cookies**: Only session token (encrypted JSON)

### PII Protection
- **Sentry**: Strips user email before sending errors
- **Logs**: No password/token logging
- **Client state**: Zustand persists minimal data (user ID, username only)

### Webhook Verification
- **Clerk webhooks**: Verified via Svix signature
- **Stripe webhooks**: Verified via `stripe.webhooks.constructEvent()`

## 19. Known Limitations & Production Checklist

### Known Limitations

1. **In-memory room state**
   - If WS server crashes, rooms lost
   - Fix: Redis persistence (BullMQ handles this)

2. **No persistent replay** (yet)
   - Room history not saved (timestamp tracking is)
   - Would require storing keystroke history

3. **Single WS server**
   - Can't scale beyond 1 server without Redis pub/sub
   - Fix: Add Socket.io Redis adapter

4. **No tournament system** (UI only)
   - Tournament page is placeholder
   - Would need bracket generation + match scheduling

5. **Limited interview features**
   - No screen share, video, audio
   - Fix: Add Twilio or Vonage

6. **Problem versioning**
   - Forked problems not used (forked_from column exists)
   - Could allow "Problem improvements" feature

## Detailed Implementation Notes

### Socket.io Connection Lifecycle
1. Client calls `connectSocket(userId, username)` from `lib/socket.ts`
2. Initializes Socket.io client with `autoConnect: false`
3. On `room:join` event, emits to server with roomCode, userId, username
4. Server adds to room, emits `room:state` to client
5. Client updates Zustand store with room state
6. Real-time events (`submission:result`, `room:started`, etc) flow bi-directionally

### Supabase to App Sync
- When user signs up via Clerk, webhook fires
- `/api/webhooks/clerk` creates entry in `users` table
- User can then use Supabase RLS-protected queries
- `useEffect` in AuthProvider queries `/api/auth/me` on app load
- Session stored in Zustand → localStorage → persists across reloads

### Code Execution Pipeline
1. User submits code in `/room/[code]`
2. POST `/api/submissions` with code + language + problemId
3. Server runs code via Judge0 (if configured) or Piston (free fallback)
4. Compare output to expected test cases
5. Update submission status in DB
6. Emit `submission:result` via Socket.io to room
7. Server broadcasts `room:progress_update` to all players
8. Client receives, updates leaderboard, shows XP toast

### Development vs Production Modes
| Feature | Dev | Prod |
|---------|-----|------|
| Auth | Local file-based | Clerk OAuth |
| Database | In-memory or local Supabase | Production Supabase |
| Code execution | Free Piston API | Judge0 (self-hosted or RapidAPI) |
| WebSocket | Local :3001 | Railway/DigitalOcean :3001 |
| Room state | In-memory + Redis | Redis (Upstash) |
| Rate limiting | In-memory | Upstash Redis |
| Email | Disabled | Resend |
| Errors | Console logs | Sentry |
